# Spec: Bridges (out-of-process connectors in Python, JVM and .NET)

Status: implemented as a library and SDKs; not wired into the runtime. Date: 2026-11-21 (written as
built on 2026-11-22).

## TLDR

A bridge is a child process that serves `nurtuo.connector.v1` over a Unix socket (loopback TCP on
Windows). The Go launcher `connectors/bridge` starts it with a minimal environment and a random
token, waits for one handshake line, dials it lazily and restarts it on crash. The Python SDK is
built and tested in CI; the JVM and .NET SDKs were written but never built in M1. The runtime does
not use any of this yet: `core/runtime/internal/bridgehost` is a placeholder and `runtime.yaml` has
no bridge configuration.

## Problem and goals

Enterprise connectivity depends on vendor SDKs that exist only for the JVM (JMS, IBM MQ, SAP JCo),
Python (data and ML libraries) or .NET (Windows-only line-of-business SDKs). They must run outside
the Go runtime process and still look like any other connector.

- Goals: one language-neutral process protocol; the same gRPC contract as native connectors; the
  bridge never inherits the runtime's environment; crash isolation with bounded restarts; one
  conformance suite for every language.
- Non-goals (as built): bridge download, signature verification, packaging, resource limits
  (cgroups, job objects), runtime configuration of bridges.

## Design (as built)

**Process protocol** (`bridges/README.md`, constants in `connectors/bridge/handshake.go`):

- Environment: an allow-list from the runtime (`inheritedEnv`: `PATH`, `PATHEXT`, `SYSTEMROOT`,
  `SYSTEMDRIVE`, `WINDIR`, `COMSPEC`, `TEMP`, `TMP`, `TMPDIR`, `HOME`, `USERPROFILE`, `APPDATA`,
  `LOCALAPPDATA`, `LANG`, `LC_ALL`, `TZ`), then `Config.Env`, then `NURTUO_BRIDGE_LISTEN`
  (`unix:<0700 temp dir>/b.sock` or `tcp:127.0.0.1:0`), `NURTUO_BRIDGE_CONTRACT` (offered
  contracts, default `nurtuo.connector.v1`), `NURTUO_BRIDGE_TOKEN` (32 random bytes hex),
  `NURTUO_BRIDGE_WATCH_STDIN=1`.
- Handshake: the first stdout line `NURTUO-BRIDGE|1|<network>|<address>|<contract>|<implementation>`
  (`ParseHandshake`): version must be 1, network `unix` or `tcp`, a TCP address must be loopback,
  the contract must be one that was offered.
- Every RPC carries the token in metadata `x-nurtuo-bridge-token`; a bridge with a token set
  answers `UNAUTHENTICATED` without it. Bridges also serve `grpc.health.v1.Health`.
- Exit codes: 0 clean, 2 cannot start, 3 no acceptable contract, other = crash.
- Stop: the launcher closes stdin, waits `StopTimeout`, then kills.

**Launcher** (`connectors/bridge/bridge.go`): `Start(ctx, Config)` launches and waits up to
`StartTimeout` (15 s) for the handshake; `Conn()`/`NewConn()` return connections whose custom dialer
always resolves to the current child (`grpc.WaitForReady`); `supervise` restarts with
`RestartBackoff` 200 ms doubling to 5 s, at most `MaxRestarts` 3 per `RestartWindow` 1 min, then
`fail` closes `Done()` and `Err()` reports why; `Close` is graceful then kills (`StopTimeout` 5 s).
`(*Bridge).Connector()` adapts the bridge to `connector.Connector`; its `Execute` proxies the stream
and returns a non-OK bridge status unchanged, never as success. The package depends only on
`sdk/go`, never on `core/`.

## Compatibility

PR #41 renames the generated descriptor type in every SDK (`Descriptor` to `ConnectorDescriptor`):
connector code in all three languages that names the type must be updated, but the wire format is
unchanged, so a bridge built before PR #41 still talks to a runtime built after it. See the
connector contract spec.

## Security

- The child gets an environment allow-list, not the runtime's environment, so `NURTUO_SECRET_*`
  values never reach a bridge (`TestEnvironmentIsNotInherited`).
- Unix sockets live in a fresh 0700 temp directory; on Windows the transport is loopback TCP and the
  token is the only authentication against other local processes (`TestTokenIsRequiredByTheBridge`).
- Bridge executables are **not** signature-verified: the launcher starts whatever `Command` it is
  given, with the runtime's privileges (`SECURITY.md`, `//nolint:gosec` comment in `launch`).
- Secrets reach the bridge in `ConnectionConfig.settings` on each call; the SDKs mask known secret
  keys (Python and the README: values shorter than 4 characters are not masked; the Go runtime
  threshold is 3).
- No TLS on the local transport; no memory or CPU limits; grandchildren are not killed on Windows.

## Gaps and risks

| # | Scenario (concrete) | Severity | Area | Mitigation / follow-up |
|---|---|---|---|---|
| 1 | A customer needs the JMS connector (`bridges/jvm/nurtuo-connector-jms`): it has never been compiled, there is no JVM CI job, and the runtime cannot start a bridge from `runtime.yaml` (`internal/bridgehost` is a doc-only placeholder; `connhost.Builtins()` registers native connectors only), so the feature does not exist for an operator | high | runtime, JVM | add a `bridge-jvm` CI job (`./gradlew test`); implement `bridgehost` (config `bridges: [{id, command, args, env}]` registering a `connhost.Factory` that returns `(*Bridge).Connector()`) |
| 2 | An attacker who can edit `runtime.yaml` or replace the bridge executable gets code execution with the runtime's privileges (LocalSystem or root when installed via `nurtuo service install`), because bridge binaries are not signature-verified | high | security | verify cosign signatures and a digest pin before `exec`; run bridges as a lower-privileged user |
| 3 | PR #41 is not merged: `bridge-dotnet` stays `continue-on-error: true`, so a .NET regression merges green | medium | CI | merge PR #41 (removes `continue-on-error`) |
| 4 | Inbound JMS/IBM MQ listeners are the main reason for the JVM bridge, but no SDK implements `Listen` and the runtime's listener factory rejects non-HTTP connector listeners (`listener: connector %q listeners are not supported by the factory`) | high | bridges, runtime | draft spec `connector-listen-operation` |
| 5 | A Python connector leaks memory; the bridge grows until the host's OOM killer picks a process, possibly the runtime itself, because there are no cgroup/job-object limits | medium | launcher | memory limits per bridge (cgroups v2 on Linux, job objects on Windows) and restart on limit |
| 6 | On Windows, a bridge spawns a helper process; `Close` kills only the direct child, the helper keeps the TCP port or files open and the next start fails | medium | launcher | assign the child to a Windows job object with `KILL_ON_JOB_CLOSE` |
| 7 | A bridge started manually without `NURTUO_BRIDGE_TOKEN` (debugging) accepts unauthenticated RPCs on loopback TCP from any local process | low | SDKs | refuse TCP without a token unless an explicit `--insecure-dev` flag is given |
| 8 | The Go runtime redacts secrets of 3+ bytes, the bridge SDKs only of 4+ characters; a 3-character secret echoed by a bridge is masked by the runtime wrapper but not in the bridge's own logs | low | redaction | align thresholds |

## Improvement opportunities

- Named pipes on Windows instead of loopback TCP once all three stacks support them.
- A bridge registry entry declaring supported contracts, so the runtime refuses an incompatible
  bridge before starting it (described in the README, not built).
- Run `contracttest` against the JVM and .NET examples from Go, like the Python test does.
