# Spec: Private DACL for the Windows standalone data root, postgres and logs

Status: draft. Date: 2026-11-25.

## TLDR

`nurtuo standalone` on Windows keeps its data root in `%ProgramData%\Nurtuo`, which inherits read and create access for the local `Users` group. Only `secrets\` is protected today (issue #57). This spec extends the same protected DACL (running account + `SYSTEM` + `BUILTIN\Administrators`) to the whole data root, including `postgres\data`, `postgres\runtime`, `postgres\cache`, `logs\` and the runtime state directory `runtime\`, and moves the ACL helpers out of `internal/secrets`. `secrets\` keeps the #57 policy (D6). It stays `draft`, with no code, until the owner answers Q1-Q6 (Open Questions).

## Problem and goals

Another local user can (a) read `postgres\data` (users, password hashes, audit records), (b) plant a binary in `postgres\runtime` that the next start runs as the Nurtuo account, (c) do the same through `postgres\cache`, if the cache is extracted to `postgres\runtime`, (d) read `logs\`, and (e) read or change `runtime\` (the runtime `state_dir`: embedded JetStream queue data in `runtime\jetstream`, the applied revision and the `lock` file). `prepareStateDir` (`internal/runtime/state.go`) creates it with mode `0700`, which sets no DACL on Windows, so it inherits the data root's DACL.

- Goals: after `standalone` starts on Windows, the data root and everything below it (except `secrets\`, which stays under #57, D6) is owned by an allowed principal and has a private DACL under D2, protected on managed roots; a too-open tree that Nurtuo manages (see Repair semantics) is repaired at startup, and an operator-owned directory is only checked, with an `icacls` hint; a foreign owner, a reparse point or a multiply-linked file fails closed; an existing Postgres cluster outside the supported standalone state (configuration or recovery files) does not start; embedded Postgres still starts; operators have a documented way to read logs.
- Non-goals: `secrets\` semantics (unchanged, #57; the data-root walk stops at `secrets\`, see D6); Unix behaviour (unchanged); operator-chosen secrets paths (D9 of the parent spec still applies); encrypting data at rest; Windows service ACLs, including the `state_dir` that `nurtuo service install` configures outside the standalone data root.

## Decisions (proposed)

Recommendations are in bold. None is approved; the owner's answer to the matching question in Open Questions decides each one.

- **D1 Shared ACL layer.** **Move the private-path helpers (`EnsurePrivateDir`, `checkPerm`, `judgeDACL`, `mkdirPrivate`, `setPrivateDACL`, `visitTree`, `aclError`) into a new package `core/runtime/internal/privacl`, and let `internal/secrets` call it.** Pure move, no behaviour change, resolves the `TODO(#78)`. Alternative: keep them in `internal/secrets` and export `EnsurePrivateDir` only (smaller diff, but the data root keeps depending on the secrets package).
- **D2 Principal set.** **Same as D4 of the parent spec: the running account, `SYSTEM`, `BUILTIN\Administrators`.** No extra "operators" group.
- **D3 Scope of the walk.** **Walk the entire existing root except the `secrets\` subtree (D6), including `postgres\data`, `postgres\runtime`, `postgres\cache`, `logs\` and `runtime\`, on every start.** Repair only in managed mode. Measure the startup cost of walking large databases before reconsidering the scope.
- **D4 Operator-chosen data root.** **Check an existing `NURTUO_DATA_DIR` without repairing it unless the root and its marker meet the trust checks below.** If the root is absent, create it with the private DACL at creation and exclusively create `.nurtuo-managed` as a regular file with its own protected private DACL. If a root appears before exclusive creation succeeds, validate it as an existing root. Leave the existing parent untouched. The check-only policy follows D9 of the parent spec.
- **D5 Rejected roots.** **Startup fails with an error, before any check or change, if the data root is a drive root (`C:\`, `\\?\C:\`, a UNC share root) or is `%ProgramData%` itself.** Also rejected: a root that is a parent of `%ProgramData%`, `%SystemRoot%` or a user profile root. The message names the offending path and asks for a dedicated subdirectory.
- **D6 Ownership of `secrets\`.** Issue #78 excludes `secrets\`. **The #57 policy owns the `secrets\` subtree in both root modes: the data-root preflight and repair treat `secrets\` as a boundary (they neither judge, repair nor report it or anything below it), and the existing `secrets.EnsurePrivateDir(secrets\)` call stays the only code that checks and repairs it, with the #57 rules unchanged (repaired in a managed root and in an operator root, as today).** D5 and the ancestor reparse check of Design step 1 still run first, because they concern the root path. `EnsurePrivateDir(secrets\)` runs before any data-root repair. The #57 checker ignores the protection bit and its repair skips objects that pass, so `secrets\` can stay non-protected with inherited D2-only ACEs. The data-root repair still never changes it: it never writes `secrets\` or anything below it, and its writes do not propagate (Repair containment), so no inheritable ACE of a repaired root reaches `secrets\`. Alternative (scope extension, needs explicit owner approval because #78 excludes it): apply this spec's rules (deny ACEs, effective access, hard links, check-only on operator roots) to `secrets\` as well, amending the #57 behaviour; the hard-link and deny-ACE gaps of #57 would then close here instead of in a follow-up (gap 5).

## Repair semantics

- **Managed root** (repair allowed) means the root selected by the Windows default when `NURTUO_DATA_DIR` is unset, a root Nurtuo exclusively created this run, or an existing configured root with a trusted `.nurtuo-managed` marker. To trust the marker, require both the root and the marker to already pass the owner, private DACL and effective-access checks below and to have protected DACLs. Inspect the marker as a regular file without following reparse points. An absent or untrusted marker grants no repair authority. Check the root as operator-chosen, including checking the marker itself if present.
- **Operator root** (check only) means any other existing configured root. Nurtuo changes no existing ACL in the tree outside `secrets\` (D6). A rejection names the offending path and reason and gives per-path `icacls` guidance for restoring the D2 grants and removing offending allow ACEs.

Both modes apply these standalone checks to the root and everything below it except the `secrets\` subtree, which keeps the #57 policy in both modes (D6). In an operator root, therefore, `secrets\` is still repaired as today; this is the one exception to check-only.

- **Owner**: must be the running account, `SYSTEM` or `BUILTIN\Administrators`. Any other owner fails closed. Repair never changes an owner (the take-ownership hint is printed).
- **Allow ACEs**: only the D2 principals; an allow ACE for any other SID, or an unknown ACE type, is too open. A NULL DACL is too open.
- **Effective access**: use the actual running token to verify rights needed on each object, such as directory traversal, enumeration and required child creation, and file read, write or execute access as applicable. An empty DACL, an inherit-only grant or a SYSTEM-only grant to a token lacking that SID is insufficient. Check-only roots fail on insufficient access. Managed paths can be repaired if safely inspectable, and must pass the effective-access check afterwards.
- **Deny ACEs**: any deny ACE (explicit or inherited) fails the check, for any SID. A deny on a D2 principal can lock Nurtuo out, and a deny on another SID is an operator rule we must not rewrite. Repair never removes or reorders deny ACEs; it refuses with the path and the ACE, in both modes.
- **Inheritance**: the private DACL is the #57 one, `D:P(A;OICI;FA;;;<running account>)(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)`. Every inheritable allow ACE (`OI` or `CI`, explicit or inherited, including inherit-only ones) on a directory is judged like a direct grant, so `CREATOR OWNER` (`S-1-3-0`), `CREATOR GROUP` (`S-1-3-1`) or any other non-D2 SID in it is too open. Required state per mode:
  - *Managed root.* The root is protected and holds exactly the private DACL; Nurtuo sets protection only on a root it manages (at creation or when repairing it) and never on the parent of the root. Each layout directory Nurtuo creates, and each object it repairs, also gets the protected private DACL. Any other descendant passes if it is either protected with only D2 allow ACEs, or not protected and its ACEs are D2-only, where the inherited ones (`ID`) are the parent's inheritable D2 grants: `(A;OICIID;FA;;;X)` on a directory, `(A;ID;FA;;;X)` on a file. In addition, every directory, the root included, must carry inheritable grants. Its ACEs with both `OI` and `CI` must give the running account at least traverse, list, add file, add subdirectory, read, write and delete. A directory with only direct D2 grants (no `OI|CI`) fails, even when protected, because files created in it later would get only the creator's default DACL. It is repaired like any other failing object. A descendant that fails is repaired by replacing its whole DACL with the protected private one, never by editing single ACEs. A repair write never propagates to children (see Repair containment): each object that needs a new DACL is written on its own, and an object that passes keeps its DACL byte for byte.
  - *Operator root.* Nurtuo changes no inheritance and no ACE on existing objects. The root and its descendants may be non-protected. Each object passes only if its effective ACEs (explicit plus inherited) satisfy the allow, deny and effective-access rules, and each directory has inheritable grants that are D2-only and give the running account at least traverse, list, add file, add subdirectory, read, write and delete with `OI|CI`, so files and directories created later (by Nurtuo or Postgres) are private and usable. A directory with only direct grants is rejected with an `icacls ... /grant <account>:(OI)(CI)F` hint. Missing layout directories Nurtuo creates in an operator root get the protected private DACL at creation.
  - *New descendants.* In both modes, an object created after startup by the running process or by Postgres under its restricted token gets only inherited D2 ACEs (owner: the running account, or `BUILTIN\Administrators` when an elevated administrator token sets that default owner) and denies every other account. This holds for the second generation too (a file in a subdirectory created after startup); the Testing table verifies this under the real tokens.
- **Reparse points**: refused in both modes; never followed.
- **Hard links and file identity**: a file's DACL belongs to the file, not to the name, so a hard link to a file outside the root would carry a repair outside it. Preflight opens every object by handle without following reparse points (`FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`) and records its identity (volume serial number and 128-bit file ID from `GetFileInformationByHandleEx(FileIdInfo)`) and its link count (`FileStandardInfo.NumberOfLinks`). Any file with more than one link is refused in both modes, before any ACL write, naming the path and the link count; the operator removes the extra link or moves the file out. An object whose volume serial differs from the root's is refused as leaving the root.
- **Repair containment**: invariant: the data-root repair writes a DACL only to an object that preflight recorded inside the root, reopened by handle with the same volume serial and file ID, and (for a file) with exactly one link, checked through that handle immediately before the write. Nothing else in the tree, and nothing outside it, is ever written, including through inheritance. Procedure, top-down:
  1. Objects are opened with `READ_CONTROL | WRITE_DAC` for repair. Writes use `SetKernelObjectSecurity` on the verified handle with `DACL_SECURITY_INFORMATION | PROTECTED_DACL_SECURITY_INFORMATION`. This call does not propagate inheritable ACEs to existing children. `SetNamedSecurityInfo` and `SetSecurityInfo` do propagate, so the data-root repair never uses them (the #57 `setPrivateDACL` keeps them for `secrets\`, D6).
  2. Handles on the root and on every directory on the path to the object being repaired are held open, without `FILE_SHARE_DELETE`, from the reopen until the end of the repair, so those directories cannot be renamed or replaced meanwhile.
  3. A directory is repaired before anything below it. Once its private DACL is written, other accounts can no longer create, rename or link entries in it. Repair then lists the directory through its handle and compares names and file IDs with the preflight record. An added, removed or replaced entry aborts the repair: no further write, startup stops, and the error names the path.
  4. Each child that needs repair is then reopened and checked (identity, and link count for a file). A mismatch aborts the repair before that child is written. After the write, the link count is read again through the same handle; a count above one stops startup. The written object is still the one preflight vetted inside the root, so the extra name points to a private Nurtuo object and gives no access outside.
  5. After the repair, a verification walk (same handle-based inspection, the rules of the root's mode, no writes) must pass over the whole tree except `secrets\`; any failure stops startup. This also catches entries created through handles opened before the repair, because they fail the owner, DACL or link-count rule.

## Design

1. On Windows, `DataDirs.EnsureReport` normalizes the path, applies D5, then inspects the existing path components (including ancestors) for reparse points without following them. Classify the root and walk any existing tree before writing anything. Managed preflight records repairable DACLs with each object's file identity and refuses foreign owners, reparse points, multiply-linked files, objects on another volume, deny ACEs and unreadable objects. Operator preflight requires every object to pass. Rejection leaves the existing ACLs and filesystem entries unchanged.
2. After preflight, in this order: (a) create a missing root with its private DACL at creation and add the marker for a newly created configured root; (b) run `secrets.EnsurePrivateDir(secrets\)` under #57 (D6), whose report entries are merged into the startup output unchanged; (c) repair an existing managed tree top-down under Repair containment, then run the verification walk, keeping owners and using only D2 principals; (d) create missing layout directories with private DACLs in either mode. The layout is `postgres\data`, `postgres\runtime`, `postgres\cache`, `logs\` and `runtime\` with `runtime\jetstream` (today `EnsureReport` does not create `runtime\`; the runtime does that later). `EnsureReport` creates both before the runtime starts, so `prepareStateDir` finds them in place and its `MkdirAll` and `Chmod` change no DACL. `runtime\lock` is walked like any other file; startup runs before the runtime takes the lock. A preflight rejection stops before (a), so `secrets\` is not touched either. Unix behavior stays unchanged.
3. Embedded Postgres: it runs as the Nurtuo account. The DACL grants that account `FILE_ALL_ACCESS` with `OI|CI`, so `initdb` and the server create files that inherit it. Windows Postgres starts with a restricted token that still contains the user SID, so access by the user ACE should work. This is a hypothesis; it must be confirmed on a real host (real-host gate R2, gap 1).
4. Document log access through the running account, `SYSTEM` or Administrators, including elevation when using the Administrators grant. Apply D2 to logs on every start.
5. Startup output lists every tightened path (`standalone: tightened permissions on ...`), as for `secrets\`.
6. After ACL validation and any repair, verify Postgres artifacts before any executable is invoked. Verify cached archives against an expected digest for the pinned version and platform obtained from a trusted source outside the data root. Trusted digest source: a SHA-256 table keyed by Postgres version, OS and architecture, committed in `core/runtime/cmd/nurtuo` next to the version pin and compiled into the binary. It is changed only in the PR that changes the pin, by a maintainer who downloads the archive from Maven Central (`io.zonky.test.postgres:embedded-postgres-binaries-*`) and checks it against the checksum Maven Central publishes; the PR states both values. The `.sha256` file that embedded-postgres fetches from the same host is not trusted (same origin, and the library skips the check when that file is missing). A platform with no table entry fails startup on Windows. Downloads use the same table. Reuse a runtime tree only if its full contents and paths match the verified distribution. If a cached archive or runtime tree cannot be verified, obtain a verified archive and extract into a fresh private directory. Start Postgres from the verified tree exclusively. Fail startup if a verified distribution cannot be prepared. Apply the gate to existing installs, including operator roots that pass preflight, and on retries. Keep `postgres\data` in place.
7. Cluster gate: a verified distribution can still load code, run commands, replicate from another server or accept weak local logins if the cluster state tells it to. On Windows, an existing `postgres\data` (one with `PG_VERSION`) starts only if it is in the *supported standalone state* below. This is an allow-list: anything not listed is refused. Otherwise startup fails closed before any Postgres executable (`postgres`, `pg_ctl`, `initdb`, `pg_controldata`) is invoked, on first start and on retries. Supported standalone state, checked after steps 1, 2 and 6:
   - *Files.* `postgres\data` passed preflight (and any repair) under steps 1 and 2, so every object in it is owned by a D2 principal, single-linked, on the root's volume and free of reparse points. `pg_tblspc\` must therefore hold no tablespace links; it must be empty. `PG_VERSION` must name the major version of the pinned distribution.
   - *Recovery state.* None of `standby.signal`, `recovery.signal`, `recovery.conf`, `backup_label` or `tablespace_map` exists. Without these files Postgres runs at most crash recovery from the local `pg_wal`. That is supported, because a stock cluster needs it after an unclean stop.
   - *Configuration sources.* Postgres reads configuration only from `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf` and `pg_ident.conf` directly in `postgres\data`. Nurtuo starts it with no server options besides the port (`embeddedpostgres.DefaultConfig()` in `standalone_db.go`), so the command line adds nothing.
   - *Settings.* In `postgresql.conf` and `postgresql.auto.conf`, every active (non-comment) line must set a parameter that `initdb` of the pinned version writes, with a value of the stated form:
     - `max_connections`: an integer from 1 to 10000;
     - `shared_buffers`, `max_wal_size`, `min_wal_size`: an integer with an optional `kB`, `MB`, `GB` or `TB` unit;
     - `dynamic_shared_memory_type`: `windows`;
     - `log_timezone`, `timezone`: a time zone name of letters, digits, `_`, `+`, `-` and `/`;
     - `datestyle`: a comma-separated list of `iso`, `sql`, `postgres`, `german`, `mdy`, `dmy` and `ymd`;
     - `lc_messages`, `lc_monetary`, `lc_numeric`, `lc_time`: a locale name of letters, digits, space, `_`, `.`, `-` and `@`, or empty;
     - `default_text_search_config`: `pg_catalog.<name>`.

     Anything else is refused: any other parameter, an `include`, `include_if_exists` or `include_dir` directive, or a value outside its form. So the list excludes, by construction, preload libraries, `dynamic_library_path`, `jit_provider`, archive, restore and recovery commands, `primary_conninfo`, `primary_slot_name`, `ssl*`, `listen_addresses`, `unix_socket_directories`, `log_directory`, `config_file`, `hba_file`, `ident_file` and `data_directory`.
   - *Client authentication.* Every `pg_hba.conf` record must have a form that `initdb -A password` writes (embedded-postgres runs it): type `local` with database `all` or `replication`, or type `host` with database `all` or `replication` and address `127.0.0.1/32` or `::1/128`; user `all`; method `password`, `md5` or `scram-sha-256`; no options. `pg_ident.conf` must have no mappings.

   The parser follows the Postgres configuration grammar (later lines win, quoted values, `#` comments, parameter names case-insensitive) and treats an unparsable line as unsafe. The allow-list is kept in code next to the version pin. Any PR that changes the pin reviews the list against an `initdb -A password` cluster of the new version and updates the committed fixtures. Nurtuo never edits cluster configuration or state files. The error names the file, the line and the setting (or the state file) and gives the recovery steps in Compatibility. A missing or empty `postgres\data` is initialised by `initdb` from the verified distribution as today. Unix behaviour stays unchanged.

## Compatibility

This applies to Windows standalone installs, including upgrades. No API, proto or flag changes, so no breaking-change gate. Unix unchanged. Behaviour changes on Windows, by upgrade case:

- *All installs.* Other local users lose access to the data root, including `logs\` and `runtime\`. Log readers must use a D2 principal (Design step 4).
- *Default (managed) root.* The first start repairs a too-open tree and prints each tightened path. A foreign owner, a reparse point, a multiply-linked file or a deny ACE stops startup with the path and an `icacls` or `takeown` hint; the operator fixes it and restarts.
- *Operator root (`NURTUO_DATA_DIR`).* Check-only (D4). A too-open tree stops startup with per-path `icacls` guidance; nothing is changed.
- *Postgres artifacts.* A runtime tree or cached archive that does not match the committed digest table is replaced from a verified download (Design step 6). An offline host with no verified archive fails startup.
- *Existing cluster (Design step 7).* A cluster outside the supported standalone state stops startup before any Postgres executable runs. Examples: a parameter outside the allow-list (also tuning ones such as `work_mem`), a `pg_hba.conf` record that `initdb` would not write, or a `standby.signal`, `recovery.signal` or `backup_label` file. A cluster that only the standalone ever touched passes. Recovery: (1) back up `postgres\data`; (2) review the file, line and setting named in the error; (3) remove that setting, record or file, or restore `postgres\data` from a backup you trust; (4) restart, and the gate runs again. Nurtuo never edits the cluster. `docs/operations.md` (phase 4) carries these steps.

## Security

Private DACLs restrict future access under D2. The Postgres integrity gate covers runtime files and cached archives that predate hardening, and the cluster gate (Design step 7) admits only an allow-listed standalone state, so cluster configuration or recovery files cannot load code, run commands, replicate from another server or open local authentication. Earlier disclosure or tampering with database contents requires separate operator assessment. Preflight fails closed on unsafe paths or ACLs that the selected mode cannot accept or repair. As in the parent spec, path-based use after verification requires protection against replacement through the parent. If an untrusted principal can replace a validated object, hold it and the relevant path components stable with Windows handles during validation and use, or fail closed. Repair stays inside the managed root: it writes only preflight-recorded, re-verified, single-linked objects through their own handles with a non-propagating call (Repair containment).

## Acceptance criteria

- WHEN `nurtuo standalone` has started once on Windows with the default root THEN a second non-admin local user gets `ERROR_ACCESS_DENIED` reading `logs\`, `postgres\data` or `runtime\`, and creating or replacing files in `postgres\runtime` or `postgres\cache` (R1).
- WHEN those objects are inspected THEN every owner is a D2 principal, every allow ACE names a D2 principal, and every directory has `OI|CI` D2 grants. On a managed root, the root and each repaired or created object has the protected private DACL; on an operator root, each layout directory Nurtuo created has it, and existing objects are unchanged.
- WHEN a managed root is too open THEN startup repairs it under Repair containment, prints each tightened path and starts. A second start reports no tightened path.
- WHEN an operator root is too open, or any root has a foreign owner, a reparse point, a multiply-linked file, an object on another volume or a deny ACE THEN startup exits 1 before any write, naming the path and the fix; ACLs and entries are byte-identical afterwards.
- WHEN an object is replaced, linked or added between preflight and repair THEN no object outside the preflight record is written, no outside file's DACL changes, and startup stops naming the path.
- WHEN the data root is repaired THEN `secrets\` and its contents are changed only by `secrets.EnsurePrivateDir`, with #57 behaviour (D6).
- WHEN the runtime or Postgres creates a file or directory after startup, also one level further down, THEN it carries only inherited D2 ACEs and the second account is denied.
- WHEN a cached archive or runtime tree does not match the committed digest table THEN no unverified binary runs, on first start or on retry.
- WHEN an existing `postgres\data` is outside the supported standalone state THEN startup fails before any Postgres executable runs, on first start and on retry, naming the file and setting; WHEN the cluster is a stock standalone cluster THEN it restarts, also after an unclean stop.
- WHEN the same code runs on Linux or macOS THEN behaviour and tests are unchanged.
- WHEN #78 is to be closed THEN gates R1-R3 are recorded as passed on a real Windows host.

### Real-host gates

CI cannot prove these, or may skip them on hosted runners (no second account, no restricted-token Postgres). Each is a hard exit criterion. Record the result in this table (date, Windows build, account types, commands run and output or a linked log) in the PR of the phase that needs it; a skipped CI row counts as not run.

| # | Gate | Needed by | Result |
|---|---|---|---|
| R1 | Second local non-admin user cannot read `logs\`, `postgres\data` or `runtime\`, and cannot create or replace files in `postgres\runtime` or `postgres\cache`, on a fresh install and on an upgraded pre-hardening install | phase 4 | not run |
| R2 | Embedded Postgres runs `initdb`, starts, restarts and survives a retry under the protected DACL with its restricted token (gap 1) | phase 3 | not run |
| R3 | The CI rows that logged `SKIPPED` (second account, SYSTEM-only as a non-SYSTEM account) pass when run by hand | phase 2 | not run |

## Gaps and risks

| # | Scenario (concrete) | Severity | Area | Mitigation / follow-up |
|---|---|---|---|---|
| 1 | Embedded Postgres fails to start on Windows under the protected DACL (restricted token) | high | runtime | real-host gate R2 before phase 3 is done; if it fails, add the needed principal only after owner approval |
| 2 | Full walk of a large `postgres\data` slows every start | medium | runtime | measure before proposing any change to D3 |
| 3 | Data root previously used by another account is foreign-owned and start fails | medium | ops | existing take-ownership hint; document in `docs/operations.md` |
| 4 | Antivirus or backup agents run as another account and lose access | low | ops | document access under an existing D2 principal |
| 5 | Under D6, `secrets\` keeps the #57 rules, which ignore deny ACEs and do not refuse multiply-linked files | medium | secrets | follow-up issue against #57 after approval, unless the owner picks the D6 alternative |
